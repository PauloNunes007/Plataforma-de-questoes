# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Questly — a gamified study-planner web app (Portuguese/pt-BR UI) for university students prepping for exams ("Bosses"). Static HTML/CSS/JS front end talking directly to Supabase (Postgres + Auth + RLS) from the browser. No backend server, no build step, no bundler, no package.json, no test suite. Every dependency is loaded from a CDN `<script>` tag in each HTML file.

## Running / developing

There is no build or lint command — open the HTML files directly in a browser, or serve the folder with any static file server (e.g. `npx serve .`) since Supabase auth redirects work better over `http://` than `file://`. To change the backend schema, run the `supabase_*.sql` files by hand in the Supabase SQL Editor, in the order noted in each file's header comment (they're additive, idempotent migrations — not a managed migration tool). `supabase_conteudo_compartilhado.sql` must run before `supabase_seed_questoes.sql`. `supabase_ementas_ciclo_basico.sql` (curricular content + skip/recap columns + basic-engineering-cycle ementas) runs after `supabase_conteudo_compartilhado.sql`; it renames the `Geometria Analítica` materia to `Fundamentos de Cálculo e Geometria` and `Programação` to `Programação I`, and adds a unique index on `topicos (materia_id, lower(nome))` (its seeds upsert on that key). `supabase_importar_revisao.sql` runs after `supabase_add_storage_imagens.sql`; it adds `questions.alternativas_imagens` (per-letter image URLs, used by the JSON reviewer importer). `supabase_ciencia_aprendizagem.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `question_attempts.motivo_erro` (check-constrained to `conceito|calculo|interpretacao|chute`) plus an owner-only UPDATE policy on `question_attempts` — without that policy the error-autopsy update in `questao.js` silently updates 0 rows (RLS filters, no error). `supabase_rotina_semanal.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds the `rotina_semanal` table (owner-only RLS) that backs the weekly per-discipline schedule (see "Weekly schedule & multi-mission days" below). `supabase_perfil_publico_stats.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `profiles.questoes_total` (lifetime question count, backfilled once from `question_attempts`) and is kept in sync going forward alongside `xp_total` — added for the Next.js ranking page's public student card, which can't sum owner-only `question_attempts` for someone else's account. `supabase_tikz_svg_mimetype.sql` runs after `supabase_add_storage_imagens.sql`; it adds `image/svg+xml` to the `questoes` bucket's `allowed_mime_types` — without it, uploading a TikZ-compiled figure (see `web/CLAUDE.md`'s TikZ section) 415s with "mime type image/svg+xml is not supported". `supabase_motor_maestria.sql` runs after `supabase_ciencia_aprendizagem.sql`; it adds `aluno_topico_progresso.maestria` (P of mastery, Bayesian Knowledge Tracing) and `.estabilidade` (memory half-life in days) as **persisted state** — a design reversal from `supabase_ciencia_aprendizagem.sql`, which derived mastery/retention on read: the predictive engine (see `web/CLAUDE.md`'s "Motor de aprovação" section) needs them persisted because BKT is sequential and stability depends on review spacing, neither reconstructible from an average. It backfills both once from the existing `taxa_acerto`/`num_questoes_respondidas` (shrinkage-seeded, so nobody restarts at cold-start) and changes no RLS (columns inherit the owner-only policy on the table). `taxa_acerto` stays for UI/telemetry and as the backfill seed. `supabase_nome_editavel.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `profiles.nome_alterado_em` (last name-change timestamp; NULL = never changed) plus a partial case-insensitive unique index `profiles (lower(nome)) where nome is not null and nome <> ''` — backing the Next.js Configurações "Nome" card, which lets a student rename (public in the ranking) but enforces uniqueness and a 15-day cooldown (both checked in `salvarNomeAction` for friendly messages; the index is the race backstop). No RLS change (profiles already reads public / writes owner-only). **Careful:** the index creation fails if two profiles already share a name — the header has a dedup query to run first. `supabase_username.sql` runs after `supabase_nome_editavel.sql` (it drops that migration's `profiles_nome_lower_key` index); it adds `profiles.username` (public @handle shown in the ranking/public student card, format check `^[a-z0-9][a-z0-9_.]{2,19}$`, case-insensitive partial unique index `profiles_username_lower_key`) plus `profiles.username_alterado_em` — the uniqueness + 15-day cooldown rules **move from `nome` to `username`** (`salvarUsernameAction` in `web/src/lib/configuracoes/actions.ts` gives the friendly messages; index + check constraint are the race backstop), and `nome` becomes a free display name (dashboard greeting/sidebar only, `salvarNomeAction` no longer gates anything). Accounts with NULL username fall back to `nome` in the ranking until the student picks an @ in Configurações. No RLS change. `supabase_tarefas_semanais.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds the `tarefas` table (owner-only RLS, same pattern as `rotina_semanal`) — pontual to-dos the student adds to a specific calendar date (nome/descrição/disciplina opcional), backing the Next.js dashboard's "Tarefas do dia" card and the calendar's day-detail panel (see `web/CLAUDE.md`). Unlike `rotina_semanal` (recurring, one weekday), each row here is tied to one `data`; no relation to `daily_logs`/streak or to `missions`. `supabase_sessoes_agenda.sql` runs after `supabase_tarefas_semanais.sql`; it adds `tarefas.tipo` (`tarefa`|`sessao`, check-constrained, default `tarefa`), `tarefas.hora` (time) and `tarefas.duracao_min` (int, 1..600) — the schema behind the Next.js home's **Agenda** card (see `web/CLAUDE.md`), where the student schedules a study block with a start time and a duration instead of only writing a to-do. Same table on purpose: both are one owner-only row tied to one `data`, and splitting them would force the agenda to run two queries and merge two arrays to draw a single day; `tipo` tells them apart. Also adds `(user_id, data, hora)` for the in-day chronological order. No RLS change (the columns inherit the owner-only policy from `supabase_tarefas_semanais.sql`). Scheduling a block deliberately does NOT feed `missions`, XP or `daily_logs`/streak — a plan is not an achievement, and letting it pay out would open a ranking-forge path. `supabase_agenda_metas.sql` runs after `supabase_sessoes_agenda.sql`; it adds `meta` to the `tarefas.tipo` check and `tarefas.meta_questoes` (int, 1..500) — the third thing a student can put on a calendar day, next to the to-do (`tarefa`) and the timed study block (`sessao`): a target of N questions in one discipline that day ("quarta, 30 questões de Cálculo II"). Backs the Next.js **dedicated calendar** (`/calendario`, see `web/CLAUDE.md`), which replaced the full-width Agenda card that used to sit at the bottom of the home. **The meta's progress is deliberately NOT stored**: how many questions were actually answered that day in that discipline is recomputed on read from `question_attempts` → `missions (subject_id, data)` (`web/src/lib/agenda/agenda-data.ts`) — a counter column would be a second home for the same truth and the obvious way to forge it. Marking a meta pays no XP, generates no mission and doesn't light the streak, same rule as a scheduled session. No RLS change (the column inherits the owner-only policy from `supabase_tarefas_semanais.sql`). **`supabase_agenda_consolidado.sql` supersedes the three agenda migrations above (`supabase_tarefas_semanais.sql`, `supabase_sessoes_agenda.sql`, `supabase_agenda_metas.sql`) — run it INSTEAD of them.** It declares the final shape of `tarefas` (columns, CHECKs, RLS, indexes) in one order-independent, idempotent script, and ends with two verification queries whose expected output is written beside them. It exists because the chained versions had two ordering traps, both of which fired in production: running `agenda_metas` before `sessoes_agenda` made the whole script revert (Supabase's SQL Editor runs a pasted script as one transaction), so `meta_questoes` was never created and EVERY insert into `tarefas` failed — `criarTarefaAction` always sends that column, even for a plain tarefa; and then re-running `sessoes_agenda` afterwards to "fix the order" recreated `tarefas_tipo_check` with only `('tarefa','sessao')`, forbidding `'meta'` again — each repair undid half of the previous one. `supabase_sessoes_agenda.sql` now includes `'meta'` in that CHECK so it is harmless in any order. `supabase_subtopico_questoes.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `questions.subtopico` (nullable text) so each question can be tagged with the specific ementa subtopic it tests (e.g. "Regra da cadeia" inside the "Cálculo das Derivadas" topico), more granular than `topicos.descricao` (one subtopics blob per whole topico). No RLS change. The Next.js importer (`web/src/lib/importar`) reads/writes it via a `subtopico` key in the imported JSON and an editable field in the review card; `/questao` shows it as a chip next to dificuldade/instituição. `supabase_admin_questoes.sql` runs after `supabase_add_storage_imagens.sql`; it adds a `DELETE` policy on `questions` restricted to a single account by JWT email (`paulocresponunes@gmail.com`, hardcoded — there's no `role` column yet, see the "sem papel de admin ainda" note above) — backs the Next.js `/admin/questoes` screen, which lets that one account edit or delete any question. `UPDATE`/`INSERT` on `questions` stay open to any authenticated user (unchanged, still used by `/importar`); only the new destructive `DELETE` capability got a DB-level gate on top of the app-layer check in `web/src/lib/admin/actions.ts`. `supabase_anotacoes_favoritos_relatos.sql` runs after `supabase_admin_questoes.sql` (reuses the same admin email in its policies); it adds three tables: `question_notes` and `question_favoritos` (both owner-only `for all` RLS, one row per `user_id`+`question_id`, same pattern as `tarefas`/`rotina_semanal`) back the Next.js `/questao` screen's per-question note/favorite toggles and the `/questoes/anotacoes`/`/questoes/favoritos` review pages; `question_reports` (a student "reportar problema" on a question — missing enunciado/image, wrong gabarito, broken LaTeX, etc.) has insert+own-select policies for any authenticated user plus two admin-only policies (select-all, update) gated the same way as the `questions` `DELETE` policy above — backs `/admin/relatos`, where that one account reviews and resolves reports. `supabase_plano_pro.sql` runs after `supabase_admin_questoes.sql`; it adds the Pro plan (columns `profiles.plano`/`plano_ciclo`/`plano_desde`/`plano_expira_em`/`plano_fidelidade_ate`, the `assinaturas` table, an admin-UPDATE policy on `profiles`, and grants the admin account lifetime Pro) — see `web/CLAUDE.md`'s plano/Pro notes and memory `plano_pro`. `supabase_seguranca_hardening.sql` runs **after** `supabase_plano_pro.sql` and is **mandatory before publishing** — it's the security-review pass. It adds a `BEFORE UPDATE` trigger on `profiles` (`questly_proteger_colunas_profile`) that blocks a normal authenticated user from changing the plano/XP/liga/streak columns (only `service_role` or the admin email may), closing the hole where any logged-in student could set `plano='pro'` or inflate `xp_total` straight from the browser console with the public anon key; it also restricts INSERT/UPDATE on `questions`/`materias`/`topicos` to the admin email (was open to any authenticated user — the importer is an admin tool, and `tempo_medio_seg` recalibration now runs via `service_role` server-side in `lib/questao/actions.ts`), and narrows `assinaturas` so the owner can only create a `pendente` row and only cancel it (activation is admin/webhook via `service_role`). Depends on the `SUPABASE_SERVICE_ROLE_KEY` env var being set server-side (see `web/PUBLICAR.md`) — without it XP/liga/Pro writes fail. The `/importar` route and every `lib/admin/actions.ts` Server Action re-check the admin email server-side. `supabase_rede_neural.sql` runs after `supabase_motor_maestria.sql` and `supabase_seguranca_hardening.sql`; it adds the `ml_modelos` table (training rounds of the P(acerto) neural net — weights JSON + validation metrics; read: any authenticated, write: service_role only, at most one row `ativo`) and `questions.tentativas_total`/`acertos_total` (global per-question counters, recomputed idempotently from `question_attempts` on each run, maintained afterwards by `registrarRespostaAction` via service_role) — see `web/CLAUDE.md`'s "Rede neural de P(acerto)" section. Training happens at `/admin/ml`; a model only goes live if it beats the BKT baseline on a temporal validation split, otherwise every projection keeps using the pure BKT motor unchanged. `supabase_modo_aprovacao.sql` runs after `supabase_seguranca_hardening.sql` (reuses the same admin email in its content-table policies); it adds the **Modo Aprovação** (vestibular Unicamp/Fuvest 2026, Next.js routes `/aprovacao*` — see `web/CLAUDE.md`), a **single-account feature**: every policy in it requires the admin email (`paulocresponunes@gmail.com`) in the JWT, so no other student can read or write any of these tables even via the raw API — the app additionally hides the nav link/floating button and redirects `/aprovacao*` for anyone else. Tables: `erros` (caderno de erros with 1/7/30-day spaced redo), `sessoes_estudo` (daily schedule-block checkboxes, unique per user/data/bloco for upsert), `metas_mensais` (unique per user/mes/ano), `simulados`, `obras_progresso` (owner+email RLS), plus content tables `cronograma_semanal` (S1–S14 weekly topics, seeded), `escada_simulados` (one Sunday, one past exam, seeded) and `obras` (the 14 required books, seeded) — admin-only read AND write — and the Storage bucket `erros-imagens` (public read for card URLs; upload/delete admin-only within the own-user folder). Completely independent of the mission engine / missions tables. `supabase_onboarding_rls.sql` runs any time after `supabase_conteudo_compartilhado.sql`; it adds the missing owner-only RLS policy on `campaigns` — without it, the campaign-link INSERT in onboarding/Configurações fails with 42501 (was silently swallowed; the Next.js `salvarCampanhaAction` now logs it and treats it as non-fatal since nothing reads `campaigns`). `supabase_prova_topicos.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `bosses.topico_ids` (uuid[], the **exam scope** — which topics the professor said fall on THIS prova, picked by the student in `/trilha`'s Boss card). NULL/empty = scope not defined → the Next.js projection/GPS fall back to the old behavior (every `cai_na_prova` topic of the materia), so existing accounts change nothing until the student marks the scope; with a scope set, `notaProjetada`, the em-risco list and the GPS route (see `web/CLAUDE.md`) consider only those topics — without this, a P1 covering 4 of 12 topics got its projected grade crushed by 8 topics that aren't even on the exam. No RLS change. `supabase_simulados.sql` runs after `supabase_conteudo_compartilhado.sql` (and, ideally, after `supabase_plano_pro.sql` — the free-plan weekly cap is checked server-side, but nothing here depends on the Pro schema); it adds the `simulados_aluno` table (owner-only `for all` RLS, same pattern as `tarefas`/`rotina_semanal`) backing the Next.js **Simulados** feature (student-facing timed mock exams from the student's own university's past papers — Next.js routes `/simulados*`, see `web/CLAUDE.md`). One row per mock exam: `instituicao` snapshot, `materia_ids`/`topico_ids`/`question_ids` (the drawn questions, order fixed at creation), `duracao_min`, `respostas` (JSONB question_id→letter, autosaved so a refresh resumes and enables per-question review), `status` (`em_andamento`|`concluido`|`abandonado`), and graded `acertos`/`total`/`nota`/`tempo_gasto_seg`. **Deliberately self-contained** — a simulado does NOT feed XP/liga/streak or the mastery/BKT engine (a timed diagnostic ≠ a farmable daily mission, and mixing would double-count and open a ranking-forge path); no relation to `missions`/`question_attempts`. Not a single-account feature (unlike Modo Aprovação): every authenticated student sees it, but the montador only has content when the bank has past papers matching their `profiles.universidade` (honest empty state otherwise). No RLS beyond the owner policy. Distinct from Modo Aprovação's admin-only `simulados` table — different table, different feature. `supabase_questao_desafio.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `questions.desafio` (boolean, default false) — a second axis next to `dificuldade`: the level says how hard, this says whether the question is exam-level at all or **aprofundamento** beyond it. It backfills the 128 compendium-style Química Geral questions (the `dificil` ones of `quimica_geral*.json`, which the owner — who took the course — judged far beyond what the UFF exam asks) by explicit id list, and changes no RLS. The Next.js app filters `desafio = false` out of **every automatic draw** (daily mission, retrieval challenge, GPS route, simulado draw and the builder's counts); the only way in is the opt-in chip in Banco de Questões, and a question that does show up carries a "Desafio · aprofundamento" badge (see `web/CLAUDE.md`). **The app queries this column, so run the migration before deploying** the code that references it. `supabase_distintivos_selecionados.sql` runs after `supabase_conteudo_compartilhado.sql`; it adds `profiles.distintivos_selecionados` (nullable `text[]`) — the ids of the achievement badges the student chose to show on their public ranking card (`MAX_DISTINTIVOS_CARD`, currently 5 — see `web/CLAUDE.md`). Not protected by the `questly_proteger_colunas_profile` trigger from `supabase_seguranca_hardening.sql` (it's a display preference, not plan/XP/liga/streak), so the normal owner-only UPDATE on `profiles` already reaches it. No RLS change. `supabase_cupons_pro.sql` runs after `supabase_plano_pro.sql` and `supabase_seguranca_hardening.sql` (reuses the same admin email in its policies); it adds `cupons` (admin-managed codes granting N days of Pro, optional usage limit and expiry, `for all` policy gated to the admin email — students have no `select` policy, validation happens server-side via `service_role`) and `cupom_resgates` (redemption log, unique on `(cupom_id, user_id)` so the same account can't redeem a code twice — the actual anti-abuse backstop). Redemption is `resgatarCupomAction` (`web/src/lib/plano/actions.ts`) — it grants the plan directly (`profiles.plano='pro'`, extending `plano_expira_em` on top of any existing Pro rather than resetting it) via the same `service_role` path as `ativarAssinatura`, **bypassing Mercado Pago entirely** (no payment, no preference, no webhook involved). Admin CRUD (`web/src/lib/admin/actions.ts`, `/admin/cupons`) can create and activate/deactivate codes but never deletes one, keeping the redemption history intact.  `supabase_escala_lancamento.sql` runs after `supabase_questao_desafio.sql` and `supabase_seguranca_hardening.sql`, and is **mandatory before deploying any code that reads the aggregate views** — the app queries them on the dashboard, trilha, Banco de Questões, onboarding, simulados and landing. It exists because of a launch audit (2026-09-15) that found the PostgREST `max-rows` ceiling (1000 rows) silently truncating every "scan `questions` and count in JS" call site — `.limit(20000)` does **not** raise that ceiling, it can only lower it, so with 2,583 questions in the bank a whole materia had already disappeared from Banco de Questões and the trilha was marking topics that have questions as "sem questões". It adds three aggregate views (`vw_questoes_por_topico`, `vw_questoes_por_instituicao`, `vw_instituicoes` — counts of shared content only, `select` granted to `authenticated`, not to `anon`), read through `web/src/lib/questly/contagem-questoes.ts`; `questly_registrar_estatistica_questao` (a `security definer` RPC that increments `questions.tentativas_total`/`acertos_total` atomically and applies the `tempo_medio_seg` moving average, replacing a read-modify-write that lost updates when two students answered the same question at once); a partial unique index `ux_missions_dia` on `missions (user_id, subject_id, data) where avulsa is not true` **plus a dedup step that must run first** (the race had already fired in production — one account had 9 missions for the same day/subject; the losers are flipped to `avulsa` rather than deleted, because `question_attempts.mission_id` references them); and the missing indexes `questions (instituicao)`, `profiles (xp_total)`, `profiles (xp_semana)` plus the `daily_logs (user_id, data)` uniqueness the streak upsert depends on. A second, undocumented limit found in the same audit and handled purely in app code: a `.in()` list becomes a querystring, and ~400 uuids (≈14 KB) already fails with "fetch failed" — see `web/src/lib/supabase/paginado.ts` (`lerPaginado`, `emLotes`, `LOTE_IN`). `supabase_email_campanha.sql` runs after `supabase_seguranca_hardening.sql` (reuses the same admin email in its policy); it backs the **mass campaign email** (the Next.js `/admin/emails` screen — see `web/CLAUDE.md`), adding `profiles.aceita_emails` (opt-out flag, default true; **not** covered by the `questly_proteger_colunas_profile` trigger since it's a contact preference, so the existing owner-only UPDATE on `profiles` already reaches it) and the `email_campanha_envios` table (one row per `(campanha, user_id)`, status `enviando|enviado|erro`, admin-only `select`, writes only via `service_role`). The unique index `(campanha, user_id)` — not a JS filter — is what guarantees one email per student per campaign when two batches overlap; a row is claimed as `enviando` **before** the provider call, so a function that dies mid-batch under-sends rather than double-sends. The recipient list is never copied into the DB: it comes from `auth.users` via `service_role` at send time. Deliberately separate from the transactional path (`app/api/auth/email-hook/route.ts`), which ignores `aceita_emails` — a signup code is a reply to something the student asked for, not marketing. `supabase_corrigir_auth_users_tokens.sql` pode rodar a qualquer momento; é um **conserto de dado**, não schema novo: troca NULL por `''` nas colunas de token de `auth.users` (`confirmation_token`, `recovery_token`, `email_change*`, `reauthentication_token`). Existe porque `supabase_seed_ranking_teste.sql` insere direto em `auth.users` sem preenchê-las, e no GoTrue elas são `string` (não `*string`) — uma linha com NULL faz a API Admin devolver 500 `Database error finding users` em qualquer listagem que a inclua, derrubando o disparo de e-mail de campanha (`/admin/emails`) enquanto login, `getUserById` e PostgREST continuam normais. O arquivo traz também o bloco (comentado) que apaga as 40 contas `seed_N@questly.test` órfãs. `supabase_simulados_fontes.sql` runs after `supabase_escala_lancamento.sql`; it redefines `vw_questoes_por_instituicao` **without** the `where q.instituicao is not null` it was born with, so the view also counts the **authored** questions (`instituicao is null`) — the ones the team wrote, which are most of the bank. It backs the Simulados montador's new **fonte** picker (see `web/CLAUDE.md`): since 2026-09-16 a mock exam is no longer restricted to the student's own university — they choose their university's past papers, another university's, the authored questions, or a balanced mix. `vw_instituicoes` deliberately keeps excluding the null row (it answers "which universities exist in the bank", and authored is not a university), and every caller that filters by university is unaffected because NULL never matches an `.in()`. **Running it is not a deploy blocker**: without it the other-university unlock works exactly the same and only the authored fonte stays hidden. `supabase_provas_oficiais.sql` runs after `supabase_simulados.sql` and `supabase_escala_lancamento.sql`, and **is a deploy blocker** (the app reads `simulados_aluno.prova_codigo` and both new views). It adds the **provas antigas oficiais**: `questions.prova_codigo` (which real exam the question came from, e.g. `fis2-uff-2023.1-p1`) and `questions.prova_ordem` (its position in that exam) — until now `instituicao` + `ano` could not tell P1, P2 and P3 of the same semester apart, so a real past paper could not be reassembled. It backfills them by explicit id list (generated by matching the source JSONs in `listas_questoes/gerado/fisica[12]_uff_*` against the bank by normalized enunciado): **31 exams, 461 questions**, only the ones whose every source question is in the bank and that have at least 10 questions — a partial transcription stays an ordinary question in the normal draw but is never offered as "the original exam". It also adds `vw_provas_oficiais` (the catalog, derived — the exam IS the set of its questions, so no metadata table to fall out of sync; **deliberately the one place with no `desafio` filter**, since reapplying a real exam is not an automatic draw), `simulados_aluno.prova_codigo` + `simulados_aluno.publico` (opt-in ranking visibility, default false) and `vw_ranking_provas_oficiais` — a **security definer** view returning only the scoreboard columns of public, concluded rows, chosen instead of a second RLS policy on `simulados_aluno` because a policy would expose the whole row (including `respostas`) and RLS cannot filter columns. See `web/CLAUDE.md` item 27. `supabase_reorganizar_topicos_calculo.sql` roda depois da seção "FUNDAMENTOS DE CÁLCULO E GEOMETRIA" atualizada de `supabase_ementas_ciclo_basico.sql` (que passou, em 2026-09-15, a semear um tópico novo `Funções Exponenciais e Logarítmicas` entre `Funções em R` e `Função Inversa` — antes disso "Funções em R" misturava domínio/módulo/polinômios/trigonometria/composição com exponencial/logarítmica num tópico só de 32 questões). Nada aqui paga XP, acende ofensiva ou entra no ranking (registrar uma falta não é estudo; se pagasse, seria a forma mais fácil de forjar ranking já inventada neste banco). No mesmo repasse, e sem migração nenhuma, o **plano grátis apertou** (teto de 30 questões/dia, 15 favoritos, 10 anotações, além do simulado semanal que já existia) — todos os tetos são impostos no SERVIDOR, e a lista completa com o ponto de checagem de cada um está em `web/src/lib/plano/limites.ts`. `supabase_cota_pdf.sql` runs after `supabase_plano_pro.sql` and `supabase_seguranca_hardening.sql`; it adds `pdf_exportacoes` (one row per document exported per week — `documento` is `missao:<id>`/`simulado:<id>`/`topico:<id>`, `semana` is the local Monday, same convention as the league) backing the **PDF export cap**, the only ceiling that applies to the **Pro** plan too (see `web/CLAUDE.md`). It exists because exporting is the one feature that takes content OUT of the app — a printed sheet keeps working after the subscription lapses — so with a ~2,600-question bank, a R$ 15 monthly plan and a non-negotiable 7-day right of withdrawal (CDC art. 49), the optimal path for someone who wants the bank was to subscribe, download everything in a weekend and ask for the money back; the e-mail watermark deters redistribution, not extraction. What is charged is a DIFFERENT document, not a file generation: the unique index `(user_id, documento, semana)` — not a JS filter — makes **reprinting free**, which is exactly what separates honest use (tweaking spacing/gabarito on the same list four times) from extraction (a new document per topic). Three ceilings live in `web/src/lib/plano/limites.ts`: `PDF_SEMANA_PRO` (12), `PDF_MES_PRO` (20 — deliberately less than 4× the weekly one, since the abuse fits inside one billing cycle) and `PDF_QUESTOES_MAX` (60 = `SIMULADO_QTD_MAX`, so no real exam is ever truncated), the last one enforced by the server simply not sending more than that. The gate runs at PAGE RENDER, not at the download click, because the PDF is assembled on the student's device from questions the page already sent — by click time the content is already out. **No write policy, on purpose** (same track as `assinatura_pagamentos`/`relatorio_envios`): a `for all` owner policy would let a student DELETE their own rows from the browser console with the anon key, i.e. reset their own counter. `registrarExportacao` fails **open** — a bookkeeping bug must never break a paid feature. `supabase_cancelamento_assinatura.sql` runs after `supabase_assinatura_recorrente.sql` and **is a deploy blocker** (`lib/plano/actions.ts` writes the new columns and the `reembolsada` status; without the migration the CHECK rejects the write *after* the money has already been refunded at Mercado Pago — money returned and subscription still marked active, the worst possible outcome). It adds `assinaturas.cancelada_em`/`motivo_cancelamento`/`reembolsada_em`/`reembolso_centavos` plus the status `reembolsada`, backing the **cancellation menu** on `/pro` (see `web/CLAUDE.md`). Two exits, with opposite consequences: **arrependimento** (CDC art. 49 — 7 calendar days from payment, no reason required, full refund; the app refunds at MP *and* revokes Pro in the same action, removing exactly the months that charge bought rather than zeroing the expiry) and **cancelar a renovação** (stops the next charge, refunds nothing, the paid month stays the student's; only exists with a real preapproval). `reembolsada` is its own status rather than a `cancelada` with an extra column: a cancelled subscription was used to the end of the paid period, a refunded one was never paid — only the second revokes Pro. No RLS change: every write here goes through `service_role`, and the owner policy from `supabase_seguranca_hardening.sql` (owner may only do `pendente → cancelada`) stays as it is — which is also what exposed a silent bug when `cancelarRenovacaoAction` finally got a screen: it updated through the student's own client, RLS filtered the active row away, and the update affected zero rows with `error` null, so the app cancelled at Mercado Pago and kept the row marked `ativa`. **Cuidado:** as seções "Mission generation" e "Weekly schedule & multi-mission days" acima descrevem o app LEGADO (`js/*.js`), que continua com o motor antigo (até 4 disciplinas/dia, 5 tópicos/missão) e não foi tocado. Elas NÃO descrevem o app Next.js — e não é pra re-sincronizar os dois: o legado ficou como referência histórica.

## Data model — shared content vs. per-student progress

This split is the main thing to understand before touching data logic, since it spans several files:

- **Shared/global** (not scoped to a user): `materias` (subject taxonomy, e.g. "Cálculo II"), `topicos` (topics under a materia, flagged `cai_na_prova`, plus `ordem` = position in the materia's ementa and `descricao` = the subtopics text; `ordem` drives the curricular order missions follow — a topic with no `ordem` sorts to the end), `questions` (belong to a `topico`, `alternativas` is a JSONB object keyed by letter (text only), `alternativas_imagens` is an optional JSONB object keyed by letter (image URL, only letters that have one), `gabarito` is the correct letter, `tempo_medio_seg` is a running estimate, optional `imagem_url` enunciado figure). Any authenticated user can read/write this content (RLS has no admin role yet — same trust level as before, see `supabase_conteudo_compartilhado.sql`).
- **Per-student**: `profiles` (name, curso, xp_total, nivel, streak_atual, dias_disponiveis, tempo_diario_min — now up to 480 (8h+), see "Weekly schedule & multi-mission days" — plus league state: `liga`, `xp_semana`, `questoes_semana`, `semana_inicio`, `foto_url`, `questoes_total` — lifetime question count, public like `xp_total`), `subjects` (a student's personal enrollment in a materia, via `materia_id`; holds `nota_desejada` and the computed `chance_aprovacao`), `bosses` (a subject's exam dates + computed `preparo_percentual`), `campaigns` (subject↔student link created alongside a subject), `rotina_semanal` (which weekday(s) each subject is scheduled on — `subject_id` + `dia_semana`, unique per user/subject/day; see below), `missions` (a generated daily plan, now one row per subject scheduled that day: `topic_ids`, `question_ids`, `qtd_questoes`, `tempo_previsto_min`, `xp_recompensa`, `concluida`, `avulsa`, `recap_topico_id` — set only on recap missions from the trilha page), `question_attempts` (answer log, plus `motivo_erro`), `aluno_topico_progresso` (per-student per-topic `taxa_acerto`/`num_questoes_respondidas`/`ultima_revisao` and `status` = `pendente`|`pulado`|`dominado` — progress lives here, not on the shared `topico`), `daily_logs` (per-day study flag, drives streak/heatmap/calendar), `historico_semanal` (closed-week league snapshots).
- **RLS visibility**: `profiles`, `subjects`, and `historico_semanal` are readable by any authenticated user (the ranking and public student card need them); writes stay owner-only. `questions` has an authenticated UPDATE policy — without it the `tempo_medio_seg` recalibration in `questao.js` silently updates 0 rows (RLS filters, no error).
- **Storage** (Supabase Storage, free tier): public buckets `avatars` (per-user folder `{uid}/avatar.jpg`, owner-only writes) and `questoes` (question figures — enunciado + per-alternative — authenticated uploads; `js/importar.js` uploads directly from the review card, client-side resized/compressed to JPEG, but a plain public image URL works too).

## Weekly schedule & multi-mission days (`js/rotina-engine.js`)

The student picks **which disciplines to study on which weekday** — the app no longer silently studies just one subject/day. This is the `rotina_semanal` table (`supabase_rotina_semanal.sql`): one row per `(user_id, subject_id, dia_semana)`, `dia_semana` in the same 3-letter lowercase format as `QUESTLY_DIAS_SEMANA` (`js/supabase-client.js`, index = `Date.getDay()`). Edited on `questly_configuracoes.html` ("Grade semanal" card — a discipline × day checkbox grid); `questly_onboarding.html` seeds a simple default (every discipline on every chosen `dias_disponiveis` day) at signup so the app is usable immediately, before there's `chance_aprovacao` data to make a smarter call.

`js/rotina-engine.js` provides the math, always editable/overridable by the student — it's a recommendation, not a constraint:
- `questlyPesoDisciplina(subject, hoje)` — a weight per subject combining exam urgency (`1/(diasAteProva+3)`, boss-less subjects default to a 60-day equivalent), weakness (`1 - chance_aprovacao/100`, defaults to neutral 0.5 with no data yet), and goal (`nota_desejada/10`), blended with the same `PESO_*` (0.45/0.35/0.20) convention as `chance-aprovacao.js`.
- `questlyRecomendarRotina(subjects, diasDisponiveis, tempoDiarioMin)` — recommends which days each subject lands on via a **weighted credit scheduler** (Weighted Fair Queuing / Deficit Round Robin, the same principle OS/network schedulers use to divide a resource by weight without starving or monopolizing): each day, every subject's credit grows by its weight; the top `questlyDisciplinasPorDia` subjects by credit get that day and have their credit debited by the mean weight. Over a week, each subject's frequency converges to its weight's proportion. `questlyDisciplinasPorDia` caps how many subjects fit a day at `tempo_diario_min / QUESTLY_MIN_MINUTOS_POR_DISCIPLINA` (75min), capped again at `QUESTLY_MAX_DISCIPLINAS_POR_DIA` (4) — that cap only shapes the *recommendation*; manual edits in Configurações aren't limited.
- `questlyApportionarMinutos(subjectsHoje, tempoDiarioMin)` — splits a single day's `tempo_diario_min` across that day's scheduled subjects proportional to the same weight, via the largest-remainder (Hamilton apportionment) method — used by `mission-engine.js` to size each subject's mission.
- `questlyBuscarRotinaCompleta`/`questlySalvarRotina` — read/full-replace the student's `rotina_semanal` rows (delete-then-insert, same pattern as overwriting `profiles.dias_disponiveis`).

## Mission generation (`js/mission-engine.js`)

`questlyGerarMissoesDoDia(user, profile)` runs on every dashboard load and is idempotent — it returns today's already-existing missions plus generates any still missing, so it's safe to call every time instead of only "if none exists":
1. Respects `profile.dias_disponiveis` — returns `{ missoes: [], semMissaoHoje: true, motivo }` on non-study days.
2. Reads the weekly schedule (`questlyBuscarRotinaCompleta`). **No `rotina_semanal` rows at all** (pre-existing accounts from before this feature) falls back to the old single-subject behavior (nearest-boss subject only). With a schedule configured but nothing checked for today, that's an intentional rest day for that day — no mission is invented, motivo points at Configurações.
3. `profile.tempo_diario_min` is split across today's scheduled subjects via `questlyApportionarMinutos` (weighted, not even) — a subject with a closer exam or lower `chance_aprovacao` gets more of the day's time, not just more days/week.
4. For each scheduled subject that doesn't already have a mission today, `questlyGerarMissaoParaSubject(user, profile, subject, tempoAlocadoMin)` runs the actual per-subject algorithm (unchanged from before this feature, just parameterized by subject + its allocated minutes instead of always "the boss subject" + the full daily budget):
   - **Curricular frontier**: only topics that (a) have questions in the bank and (b) aren't `pulado`/`dominado` are eligible. Among the eligible, the *frontier* is the first-by-`ordem` topic not yet covered (`num_questoes_respondidas < COBERTURA_TOPICO_QUESTOES`, currently 5). The mission draws only from the frontier + earlier topics (revision) — **it never jumps ahead in the ementa**. Topics with no questions don't block the frontier (ementas vary by university; the frontier steps over them). When everything is covered, it switches to pure-revision mode over all eligible topics.
   - Eligible/frontier-scoped topics are scored by: a `BONUS_FRONTEIRA` so the new frontier topic almost always makes the cut, `cai_na_prova` weight, low `taxa_acerto` (weak content), Ebbinghaus retention (see "Learning science" below, with `BONUS_REVISAO_URGENTE` for overdue topics), and extra weight for weak topics when `nota_desejada >= 9`.
   - Top `MAX_TOPICOS_POR_MISSAO` (5 — raised from the original 3 so a subject with hours allocated doesn't run dry) topics are kept; candidate questions are shuffled, overdue-review and frontier questions front-loaded, then greedily added until the *allocated* minutes are filled (respecting `MIN_QUESTOES`/`MAX_QUESTOES`, the latter raised to 40 — the original ceiling of 15 was tuned for a single ~30min/day budget and felt shallow once a student can allocate a 2h+ block to one subject).
   - The exact `question_ids` are fixed on the mission row at creation time (not just `topic_ids`) so the displayed time estimate is a real sum, not a re-sampled average — `questao.js` prefers `question_ids` and only falls back to querying by `topic_ids` for missions created before this existed.
5. A subject with no eligible topics/questions yet is skipped without blocking the other scheduled subjects' missions that day.

## XP economy

XP per question is difficulty-weighted via `questlyXpDaQuestao` in `supabase-client.js` (`facil: 3, medio: 5, dificil: 8`, fallback 5) — mission `xp_recompensa` is the exact sum over the chosen questions, and `questao.js` pays the same weights per correct answer. A question the student already answered correctly in a past attempt pays half XP (anti-farming; `questao.js` preloads the set from `question_attempts`). Finishing a mission bumps `xp_total` and the weekly `xp_semana`/`questoes_semana` counters together (`atualizarXpELiga`).

## Weekly ranking & leagues (`js/liga.js`, `js/ranking.js`)

Five leagues (bronze→diamante), weekly rounds keyed by the local-time Monday (`questlySegundaDaSemana`). There is no server cron: rollover is lazy — `questlyGarantirSemanaLiga` runs wherever league state is needed and, if the profile's `semana_inicio` is stale, snapshots the closing week into `historico_semanal`, computes the fate, and resets the counters. Promotion/demotion is decided by the pure function `questlyDestinoNaLiga` (the ranking page paints its zones with the same function, so display always matches outcome). Rules: competition ranking on strictly-greater XP counts (deterministic ties — tied-at-top all promote; a tied group only demotes if the whole group fits in the zone), promotion requires `xp_semana > 0`, demotion only exists when the group has ≥ 5 members (small-sample protection), quotas are 30%/30%. When touching this math, keep the function pure and deterministic — every client must independently reach the same verdict.

## Approval-chance heuristic (`js/chance-aprovacao.js`)

`questlyCalcularMetricas` is a pure function (no Supabase calls — caller fetches data, this just computes) combining coverage (`num_questoes_respondidas` vs. `META_QUESTOES_TOPICO`), precision (`taxa_acerto` weighted by volume), and recent study frequency into `chanceAprovacao`. It explicitly returns `null` (not a low number) when a data-sufficiency gate isn't met (`MIN_QUESTOES_TOTAL`, `MIN_FRACAO_TOPICOS_TOCADOS`, `MIN_DIAS_COM_ESTUDO`) — the UI must show "no data yet" rather than a fabricated percentage. This is explicitly documented as a transparent heuristic, not a validated prediction — don't make it look more authoritative than that. It's invoked from `questao.js`'s `atualizarMetricasSubject` after each mission finishes, writing `bosses.preparo_percentual` (coverage only) and `subjects.chance_aprovacao` (full formula). `atualizarMetricasSubject` **excludes `status='pulado'` topics** from the topic list it passes in — a self-declared skip shouldn't count as 0% coverage dragging the chance down; `dominado` topics stay in because the recap gave them real data. The coverage threshold is duplicated as `META_QUESTOES_TOPICO` here, `COBERTURA_TOPICO_QUESTOES` in `mission-engine.js`, and `COBERTURA_TOPICO` in `trilha.js` (chance-aprovacao.js isn't loaded on the dashboard/trilha pages) — keep all three in sync.

## Skip / recap (mid-semester entry)

A student who joins after the term started shouldn't grind through content they already know. On `questly_trilha.html` each ementa topic can be **pulado** (self-declared "já sei" → `status='pulado'`, no XP, removed from daily missions and from the approval-chance denominator; reversible from the same page) or proven via a **recap**: a short single-topic `avulsa` mission with `recap_topico_id` set. `questao.js`'s `avaliarRecap` (called in `finalizarMissao`, before `atualizarMetricasSubject`) reads that field and, if the score ≥ `RECAP_APROVACAO` (0.7), sets `status='dominado'`; recaps pay normal XP because the student answered real questions. Both statuses drop the topic out of `mission-engine.js`'s eligible set, which is what lets the curricular frontier advance past already-known early topics.

## Learning science (mastery, spaced repetition, retrieval, metacognition)

Four mechanisms layered on the existing tables — no new tables, no RLS model change (see `supabase_ciencia_aprendizagem.sql`):

- **Mastery (`questlyEhMestre` in `supabase-client.js`)**: a topic is "Mestre" when `taxa_acerto >= QUESTLY_MAESTRIA_TAXA` (0.9) with `num_questoes_respondidas >= QUESTLY_MAESTRIA_MIN_QUESTOES` (20). It's *derived* from `aluno_topico_progresso`, never stored. UI: gold `🏅 Mestre` badge on the trilha, and the dashboard mission banner goes gold ("Missão de Mestre") when every `topic_ids` topic is mastered. Correct answers in a topic that was already mastered *at mission start* pay `QUESTLY_MAESTRIA_MULT_XP` (1.5×), applied after the repeat-half rule (`questao.js` snapshots `topicosMestreInicio` on load so the rate can't flip mid-mission). `questao.js` also celebrates newly-crossed masteries on the result screen (`celebrarNovasMaestrias`).
- **Spaced repetition (Ebbinghaus)**: `questlyRetencaoTopico` estimates retention `R = e^(-t/S)` where `S` (stability, days) grows with volume × accuracy (`questlyEstabilidadeDias`). In `mission-engine.js`, a covered topic with `R < QUESTLY_RETENCAO_LIMIAR` (0.6) becomes *revisão urgente*: it gets `BONUS_REVISAO_URGENTE` (45, deliberately > `BONUS_FRONTEIRA`) and its questions are front-loaded *before* the frontier's new-content dose — overdue memory beats new content. The frontier/never-jump-ahead invariant is untouched (urgent topics are always at-or-before the frontier by construction).
- **Retrieval practice**: after finishing a non-`avulsa` mission, `prepararDesafioRecuperacao` (`questao.js`) offers one random question from a topic untouched for 7+ days (`DESAFIO_DIAS_SEM_TOCAR`), scoped to the student's own materias. Accepting creates a 1-question `avulsa` mission (so it never chains into another challenge and doesn't occupy the daily slot).
- **Metacognition (error autopsy)**: on a wrong answer, `questao.js` shows optional chips writing `question_attempts.motivo_erro` (update of the just-inserted attempt row — needs the UPDATE policy from `supabase_ciencia_aprendizagem.sql`). `atualizarMetricasSubject` counts the student's classified errors for the materia and passes them as the optional 5th arg of `questlyCalcularMetricas`; `PERDAO_POR_MOTIVO` (chance-aprovacao.js) refunds a fraction of each error into an *adjusted* precision used only in the score (`calculo` 0.5, `interpretacao` 0.3, `conceito`/`chute` 0) — displayed precision stays raw, and unclassified errors keep full penalty, so the param is fully backward-compatible.

## Conventions

- All UI strings, and most function/variable names, are in Portuguese matching the app's domain vocabulary (missão, disciplina, prova/boss, trilha, cobertura, preparo). Keep new code consistent with this rather than switching to English identifiers.
- Cross-page reusable functions (in `supabase-client.js`, `mission-engine.js`, `chance-aprovacao.js`) are prefixed `questly` to avoid name collisions with page-local scripts that define similarly-named helpers (e.g. `escapeHtml`, `embaralhar` are redefined per-file rather than shared).
- Dates from Supabase (`timestamptz`) are normalized to `YYYY-MM-DD` with `String(x).slice(0, 10)` before comparing or feeding an `<input type="date">` — a raw timestamp string silently blanks a date input.
- `questions.tempo_medio_seg` is continuously recalibrated via an exponential moving average (`anterior*0.7 + novo*0.3`) as students answer, so mission-engine's time budgeting improves over time instead of relying on the CSV-import-time estimate forever.
